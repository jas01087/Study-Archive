## 1. 이미지 프롬프트 이론 — 구조화·구성적 프롬프팅

### 1.1 Structured Diffusion Guidance (Feng et al., ICLR 2023)

디퓨전 모델은 텍스트 인코딩과 이미지 latent 사이를 cross-attention으로 잇습니다. 이 논문은 프롬프트를 구성요소(명사구 등)로 분해해 각각을 attention의 key/value에 개별 바인딩하는 **학습 불필요(training-free)** 기법을 제안했습니다. 결과적으로 "파란 사과와 빨간 컵" 같은 다객체·다속성 프롬프트에서 색이 엉뚱한 객체로 번지는 현상이 줄고, ABC-6K 벤치마크에서 Stable Diffusion 대비 우위(42.2% vs 35.6% 선호)를 보고했습니다.

> **가이드 함의:** 7-슬롯은 이 메커니즘의 사람용 버전. 각 슬롯 = 모델이 독립 바인딩할 깨끗한 의미 단위.

### 1.2 RPG — Recaptioning, Planning, Generating (arXiv:2401.11708)

생성 전에 LLM으로 프롬프트를 재서술하고 영역별로 계획한 뒤 생성하면 복잡한 구성의 정확도가 올라갑니다. **02번 메타 프롬프트가 곧 "Planning" 단계**입니다.

### 1.3 Nano Banana 2 프롬프팅 특성

- Google 공식 공식: `[Subject]+[Action]+[Location/Context]+[Composition]+[Style]`
- 4규칙: 구체성 / 긍정 표현 / 카메라 통제 / 대화형 반복
- **자연어 서술형**(키워드 나열 아님)을 선호. 강한 동사로 시작 권장.
- 편집 일관성·공간 추론·텍스트 렌더링에 강함 (Midjourney=예술 스타일, SD=기술적 통제와 대비)

## 2. 메타 프롬프팅 (프롬프트를 만드는 프롬프트)

- **Suzgun & Kalai, Meta-Prompting (arXiv:2401.12954):** 작업 비종속 스캐폴딩으로 LLM을 "지휘자"처럼 동작시킴. Python 인터프리터 결합 시 표준 +17.1%, 전문가(동적) 프롬프팅 +17.3%, 멀티페르소나 +15.2% (GPT-4 기준, Game of 24·Checkmate-in-One·Python Puzzles).
- **Meta Prompting for AI Systems (arXiv:2311.11482):** 메타 프롬프팅을 "작업→구조화 프롬프트" 매핑 함수(functor)로 형식화. Recursive Meta Prompting = 자기개선 루프.
- **신뢰성 패턴:** 출력 스키마 고정 + few-shot + 낮은 temperature. → 배치 형식 일관성의 핵심.

## 3. LLM-as-a-Judge & 자동 프롬프트 최적화

### 3.1 LLM-as-a-Judge

- **분석형 루브릭**(항목별)이 홀리스틱 단일 점수보다 우월 — 실패 원인 추적·모니터링 용이.
- **1~5점 + 앵커**, **근거 먼저 채점**, **temperature 0**.
- 네 가지 편향: **위치·장황함·자기선호·표면유창성**. 순서 무작위화·명확한 루브릭·다중 심사로 완화. "완화는 선택이 아니라 설계 요건."
- **정답셋 보정** 권장 (Cohen's κ ≳ 0.6, Krippendorff's α ≈ 0.8 수준 목표).

### 3.2 반복 개선 루프 계보

- **Self-Refine (NeurIPS 2023):** 단일 모델 생성→비평→수정. 7개 과제(GPT-3.5/ChatGPT/GPT-4)에서 평균 +20%p, 일부 과제 최대 +49%p. 정지 조건="더 개선 불필요 or 최대 반복".
- **Reflexion (NeurIPS 2023):** Actor·Evaluator·Self-Reflection 분리 + 에피소드 메모리. AlfWorld +22%, HotPotQA +20%, HumanEval +최대 11%.
- **APE (arXiv:2211.01910):** 지시문 자동 생성·채점·선택. 21/24 과제에서 사람 작성 프롬프트 동급/초과.
- **OPRO (arXiv:2309.03409, DeepMind):** 옵티마이저 LLM이 과거 프롬프트+점수를 읽고 더 나은 걸 제안. GSM8K +8%, BBH +최대 50%.
- **DSPy / MIPROv2 (Stanford):** 프롬프트를 컴파일 파라미터로 — 지시·few-shot 공동 베이지안 최적화. "프롬프트를 코드처럼" 다루고 싶을 때.

### 3.3 03번 Evals 설계와의 연결

03의 7축 루브릭 + 3회 최소/10회 최대 + 실패 시 원인 보고는 위 계보의 종합입니다: 채점=LLM-as-a-judge 분석형, 루프=Self-Refine 정지 조건, 실패 보고=Reflexion 반성 메모리, 전체 구조=Anthropic evaluator-optimizer 워크플로.

## 4. 에이전트·브라우저 자동화

### 4.1 Building Effective Agents (Anthropic, 2024)

- **워크플로**(코드로 미리 정의된 경로) vs **에이전트**(LLM이 동적으로 자기 과정을 지휘) 구분.
- 핵심 원칙: "가장 단순한 해법 먼저, 필요할 때만 복잡도 증가. 워크플로는 잘 정의된 작업에 예측 가능성·일관성 제공."
- 관련 워크플로: **Prompt chaining**(순차), **Routing**(분류 후 분기), **Parallelization**(독립 하위작업 병렬), **Orchestrator-workers**(리드가 동적 분배), **Evaluator-optimizer**(생성↔평가 루프).

### 4.2 Claude in Chrome / Cowork

- Chrome 확장: 페이지 관찰 + 자동화 API로 클릭·입력·멀티탭. 저장형 워크플로·예약.
- Cowork: 데스크톱 에이전트. 로컬 파일 조작·정리, 서브에이전트 조율, Chrome 연동.
- **보안:** 레드팀 결과 인젝션 성공률 23.6%(무방어)→11.2%(자율+방어)→최신 약 1%(적응형). 단 실제 우회 시연 존재(화이트리스트 도메인 경유 데이터 유출). **관리 대상이지 해결된 위험 아님.**

## 5. 멀티에이전트 오케스트레이션 — 언제 쓰고 언제 피하나

### 5.1 효과 있는 경우 (Anthropic Multi-agent research system, 2025)

- 리서치처럼 **넓게 펼쳐지는 병렬 탐색**: 오케스트레이터-워커로 90.2% 성능 향상 보고.
- 단 **토큰 약 15배** — 작업 가치가 비용을 정당화해야 함.

### 5.2 피해야 하는 경우

- "**모든 에이전트가 같은 컨텍스트를 공유**해야 하거나 **의존성이 많은** 도메인은 현재 부적합."
- "대부분의 코딩 작업은 리서치보다 병렬화 가능 부분이 적고, LLM 에이전트는 아직 실시간 조율·위임에 능숙하지 않다."

### 5.3 본 워크플로 판정

주제→리스트→프롬프트→생성→다운로드→정리 = **순차·공유 컨텍스트·의존성 높음** → 오케스트레이션 안티패턴. **단일 선형 파이프라인 + 서브주제 이미지 생성만 병렬 팬아웃**이 최적. (상세: `04` 2절)

## 6. Gemini / Nano Banana 최신 동향 (2025~2026)

> **주의:** 모델명·ID·토큰 한도·가격은 빠르게 바뀝니다. 게시 직전 Google AI Studio / Vertex AI 공식 문서로 재확인하세요. 일부 서드파티 가이드는 Nano Banana 2와 Nano Banana Pro를 혼동합니다.

### 6.1 모델 라인업 (보고 시점 기준)

| 통칭 | 모델 ID | 포지션 |
|---|---|---|
| Nano Banana (1세대) | `gemini-2.5-flash-image` | 초기 Flash 이미지 |
| **Nano Banana 2** | `gemini-3.1-flash-image` | 속도·대량용. Gemini 3 추론 + Flash 속도 |
| Nano Banana Pro | `gemini-3-pro-image` | 복잡 구성·최고 텍스트 충실도(thinking) |

### 6.2 Nano Banana 2 주요 스펙 (재확인 대상)

- 입력 컨텍스트 **131,072 토큰** (Pro 65,536), 출력 최대 **32,768 토큰**
- 네이티브 해상도 **0.5K / 1K / 2K / 4K**
- 종횡비: 1:1, 3:2, 2:3, 3:4, 4:3, 4:5, 5:4, 9:16, 16:9, 21:9 등
- 참조 이미지 **최대 14장**
- 지식 컷오프 **2025년 1월**, 실시간 **Google Search 그라운딩**
- 모든 출력에 **SynthID + C2PA Content Credentials**(워터마크·출처)

### 6.3 실무 시사점

- **생성은 채팅창 우선(비용):** 채팅(구독 정액)은 한도 내 한계비용 0, API는 장당 과금. 평상시 배치는 Claude in Chrome으로 채팅 UI를 구동하는 게 비용상 유리. API는 채팅 한도 초과/결정론적 대량 처리가 필요할 때의 오버플로(이때 Batch ~50% 저렴, 해상도/종횡비/그라운딩 통제 가능).
- **2모델 티어링:** Nano Banana 2로 초안·반복(빠름) → 합격한 최종본만 Pro로 재생성(최고 충실도). 둘 다 채팅 한도 내에서 가능.
- **출처 표기:** C2PA/SynthID가 자동으로 붙으므로 사내·외부 배포 시 AI 생성 표기 정책과 연동.

## 7. 더 나은 파이프라인 제안 (종합)

> 전제: 생성 자체는 **채팅창 기반 브라우저 자동화**가 비용상 정답(한계비용 0). 아래는 그 위에 얹는 개선이며, API 전환이 아님.

1. **결과물 기준 evaluator-optimizer 루프** — 다운로드된 *이미지*를 멀티모달 심사에 다시 넣어 7축 채점·자동 합격. 채팅 기반에서도 이미지 첨부로 그대로 작동. 프롬프트가 아닌 결과물로 루프를 닫음.
2. **프롬프트=버전관리 코드 (DSPy식)** — 메타 템플릿·주제별 채움을 repo로 관리해 점수 재현성·회귀 추적.
3. **2모델 티어링** — Nano Banana 2 초안 → Pro 파이널 (둘 다 채팅 한도 내).
4. **워크플로 저장·예약** — Claude in Chrome의 저장형 워크플로/예약으로 반복 배치 재사용.
5. **(스케일 시에만) Batch API** — 채팅 한도를 명백히 초과하는 대량·결정론 처리가 필요해지면 검토. 장당 과금이지만 Batch ~50% 저렴.
